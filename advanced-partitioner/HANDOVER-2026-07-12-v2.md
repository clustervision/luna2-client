## HEADLINE FINDING — parity/raid10 degraded boot (BE-B10, NB-10)
The v1 handover called raid5/6 degraded-`grub>` a "GRUB limitation, use raid1/raid10". This
session tested that to destruction on lpx-node003/004:
- **raid10 degraded ALSO fails** at `grub>` → **only raid1** is a degraded-bootable OS RAID.
- **The ESP stub is NOT the failure** — serial-instrumenting it proved `search --fs-uuid` finds
  `/boot` on a raid1 member and `configfile` is reached.
- **The MAIN `/boot/grub2/grub.cfg` fails NON-DETERMINISTICALLY** under a degraded parity/striped
  array (diag3: main ran-and-fell-through; diag4: main never executed — same config). Main cfg
  already uses `terminal_output console` (gfxterm ruled out). Matches GRUB's known intermittent
  degraded-array resolution.
- A candidate stub-`insmod` fix was implemented, HW-tested (regression 3.62), and **REVERTED**.
- **Mitigation shipped (NB-10):** verify-time WARN + docs — raid1 only for degraded-bootable OS.
- **OPEN (next):** the real fix is deeper GRUB main-cfg degraded-path debugging. Reproduce with
  `drv-r6-diag.sh` / `drv-r6-diag2/3/4.sh` in `/root/lpart-uefi-work` (instrument the MAIN cfg
  with per-menuentry echoes to see where it aborts).

## Harness lessons (baked into `reg-orch.sh` — keep these)
- **Install kernel needs `console=ttyS0,115200n8`** (`luna osimage change -qo`) or the installer
  is silent on serial. (Set on lpx compute-image.)
- **lpart-internal text logs to the CONTROLLER `/var/log/cluster-messages/<node>.messages`**, not
  serial (the TUI eats stdout) → `ctrl_log_wait`/`ctrl_log_since` in reg-orch.sh.
- `console_follow` (tail -F) survives the `append='off'` truncation at the installer auto-reboot.
- `install_clean` enforces reset_nvram + **blank ALL disks**; `memboot_helper`/`sanitize_cycle`
  must blank the node's disks too (a stale ESP on any disk traps OVMF at `grub>`).
- `degraded_pull` refuses without a preceding `install_clean` (kills v1's stale-NVRAM false reads).
